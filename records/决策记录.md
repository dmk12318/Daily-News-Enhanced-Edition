# 决策记录

## 2026-10-07 时间窗按抓取时刻算，不按日历日

- 背景：新闻源各自更新节奏不同，跨时区，按「当天」切会漏掉或重复。
- 选项：按日历日切；按抓取时刻往前推 24 小时。
- 决定：窗口 = `[fetched_at - 24h, fetched_at]`；一律 UTC 计算，展示转北京时间。
- 原因：口径统一、可追溯，不用给每个源单独定规则。
- 影响：所谓「当日 08:00 回退 24 小时」等价于 `[前一日 00:00, 当日 00:00]` UTC。

## 2026-10-07 抓取失败时不假装最新

- 背景：某源可能临时挂掉或超时。
- 选项：跳过该源；用上次成功数据但不标注；用上次数据并标注时间。
- 决定：用上次成功数据，并在日报里标注「该源数据截至 HH:MM」。
- 原因：宁可说明数据边界，也不要让读者以为是实时。
- 影响：日报要写明「数据截至北京时间 08:0X（抓取时刻）」。

## 2026-10-07 影响力星级用综合估算，不用单一指标

- 背景：要排优先级，就得给源打分。
- 选项：按发行量排；按网站流量排；综合估算。
- 决定：综合「发行量 / 数字订阅 / 网站流量 / 转载被引」估到 1–5 星。
- 原因：纸质发行量和数字触达不可直接比较，单一指标会误导。
- 影响：星级是估算，不是精确排名；调整口径要同步改 `README.md` 的说明。

## 2026-10-07 抓取分三步走，用标准库不装依赖

- 背景：要能长期跑，不想依赖第三方包和额外安装。
- 选项：直接写 HTML 爬虫；用 RSS + 标准库；用 scrapy/playwright 之类的框架。
- 决定：`discover_feeds`（找 RSS）→ `fetch`（抓取落库）→ `digest`（出日报），
  全部只用 Python 标准库（`urllib`、`xml.etree`、`sqlite3`、`zoneinfo`）。
- 原因：安装第三方包属于要单独批准的事，且 HTML 爬虫脆、维护成本高；RSS 覆盖够用。
- 影响：297 个源里 105 个能拿到 feed；剩下 192 个要走 HTML 兜底或人工补地址。

## 2026-10-07 时间窗口必须卡上下限

- 背景：首轮实测混进 107 条「发布时间晚于抓取时刻」的脏数据。
- 选项：只卡下限；上下都卡；上下都卡再加容差。
- 决定：只保留 `[window_start, fetched_at + 2h]` 内的条目，超出直接丢弃。
- 原因：源端时间戳会不准甚至给出未来时间，只卡下限会把它们当成本期新闻。
- 影响：`fetch.py` 的 `window_end` 是容差旋钮，需要收紧时改这里。

## 2026-10-07 时间戳不带时区时按源清单的「时区」列解释

- 背景：首轮实测里，台湾源的时间被当成 UTC，条目跑到了第二天。
- 选项：一律当 UTC；按源清单的「时区」列解释；按抓取时区解释。
- 决定：`parse_feed` 接收 `default_tz`，由 `fetch.py` 按源名从清单取「时区」列传入。
- 原因：这是清单里专门留的一列，规则写在 `README.md` 就不能只在文档里落着。
- 影响：`lib.tz_for()` 优先用 `zoneinfo`，Windows 缺时区库时退回内置偏移表（夏令时有 1 小时误差）。

## 2026-10-07 源清单只留 3 星及以上

- 背景：2 星及以下源数量多但产出价值低，还要占用抓取和排查成本。
- 选项：全留；只留 3 星以上；按可达性筛。
- 决定：境内 59 条、境外 160 条，只留 3 星及以上；2 星全部删除。
- 原因：抓取预算有限，先把高价值源做扎实。
- 影响：`README.md` 与 `AGENTS.md` 的条数说明同步更新；低于 3 星的源不再维护。

## 2026-10-07 可见性差（不可达）的源必须一一解决

- 背景：219 个源里只有 105 个有原生 feed；境内源尤其差（59 个里 7 个）。
- 选项：只留下有 feed 的源；用 RSSHub 补；用 HTML 兜底抓。
- 决定：三条一起上——原生 feed 优先，RSSHub 补有路线的站，RSSHub 没有的走 HTML 兜底。
- 原因：用户要求 3 星及以上源必须可达。
- 影响：需要新增 `rsshub_feed` 与 `html_fallback` 两个脚本；公共 RSSHub 实例不稳，
  自建 RSSHub 属于安装动作，要先审批。

## 2026-10-07 定时用 Codex automation，发布用 GitHub Pages

- 背景：日报要每天自动出，并且要有个固定网址能直接打开。
- 选项：定时用 Codex automation / Windows 计划任务 / GitHub Actions；
  发布用 GitHub Pages / 对象存储 / 自建站点。
- 决定：定时走 Codex automation；发布把 `site/` 的 HTML 推到一个 GitHub 公开仓库，
  开 Pages 拿固定网址。
- 原因：都免安装、免服务器；Pages 免费且直接给 `https://<用户名>.github.io/<仓库名>/`。
- 影响：新增 `scripts/render_html.py` 与 `news-push` skill；发布是对外写入，
  每次推送前仍需确认；免费版 Pages 要求仓库为 public，日报内容等同全网可见。

## 2026-10-07 分类改成「选稿 + 分类」一步走

- 背景：关键词分类只认中英，西语/葡语/俄语标题全落进「社会」（47%），且 2467 条里
  绝大多数根本不该进日报。
- 选项：继续堆关键词；把全部条目丢给 LLM；先选稿再让 LLM 分类。
- 决定：`classify.py --export --per-source 1` 选出候选（每源最多 1 条、高星优先），
  LLM 判栏目并同时完成选稿，`--apply-index` 按序号回写，命中即标记 `selected=1`。
- 原因：把 LLM 的工作量从 2467 条压到 ~70 条，既跑得动，又顺带解决了「选什么进日报」。
- 影响：`digest.py` 优先渲染 `selected=1`；栏目最高占比降到 22%；一期 HTML 从 1.3 MB 降到 39 KB。

## 2026-10-07 HTML 兜底分两步，噪声交给选稿兜掉

- 背景：219 个源只有 72 个有原生 feed，覆盖面不到三分之一。
- 选项：只留有 feed 的源；用无头浏览器；抓首页抽链接。
- 决定：第一步用 `html_fallback.py` 抓首页抽头条（trafilatura 抓正文内链 + 文章 URL 特征过滤），
  并用 `--enrich` 读文章页补发布日期；第二步再单独啃被反爬/被墙的那批。
- 原因：trafilatura 抓正文内链能自动滤掉大部分导航；补日期是为了让条目能进 24 小时窗口。
- 影响：覆盖源从 72 涨到 138；抽到的条目仍有约一成是栏目页/署名，**由 LLM 选稿环节兜掉**
  （不选它就不进日报），不追求在抓取阶段做到零噪声。

## 2026-10-07 浏览器用系统 Edge，不下载 Chromium

- 背景：`playwright install chromium` 走 cdn.playwright.dev，实测卡在 0 MB 十几分钟下不动。
- 选项：挂代理下载；用国内镜像；直接用系统已装的浏览器。
- 决定：`channel="msedge"` 用系统 Edge，完全不下载；`--channel chrome` 可切 Chrome。
- 原因：Windows 必装 Edge，零下载、零 C 盘占用，也绕开了 CDN 问题。
- 影响：`browser_fallback.py` 与 `probe_url.py` 依赖系统浏览器；换机器时确认有 Edge 或 Chrome。

## 2026-10-07 「被反爬」有一半其实是域名写错了

- 背景：48 个源用 urllib 和真实浏览器都打不开，一度判断为反爬。
- 选项：直接上代理；先逐个诊断域名。
- 决定：写 `probe_url.py`，把 https/http × 带不带 www 都试一遍。
- 原因：实测 `chinanews.com.cn` 连不上、`www.chinanews.com.cn` 直接 200——
  **清单里的「官网」列大量漏写 `www.`**。`lib.fetch_home()` 现在自动展开候选起点。
- 影响：可达源从 99 涨到 116（+17），与反爬无关，纯属自己的数据错误。

## 2026-10-07 浏览器指纹救不了被 IP 封的站

- 背景：想用真浏览器过掉剩下打不开的源。
- 选项：上 Playwright；上代理；放弃这批。
- 决定：先上 Playwright 试，只对失败源触发。
- 原因：实测 31 个里只多通了 9 个（CNN、镜报、快报、RFI、RT、每日新闻、信使报、
  Interfax、France 24）；剩下 22 个**浏览器拿到的 401/403 与 urllib 完全一致**
  （路透 401、彭博 403、纽时 403、经济学人 403……），说明是服务端按 IP/地区封，
  换指纹没用，只有代理能解。
- 影响：Playwright 保留但定位收窄为「补漏」；被 IP 封的 22 个暂不处理，除非决定上代理。

## 2026-10-07 实测 Scrapling / curl_cffi，结论是不采用

- 背景：用户提出用 GitHub 上的 Scrapling（8.6 万星）替换现有抓取方案。
- 选项：整体换成 Scrapling；局部借用它的 curl_cffi 抓取器；维持现状。
- 决定：**不采用 Scrapling**；只装 `curl_cffi` 做了一次验证性测试，之后也不进主流程。
- 原因：三条——
  1. Scrapling 不读 RSS。我们 72 个源靠 RSS 十秒搞定，换过去等于用抓 HTML 替代结构化 feed，是倒退。
  2. 它的看家本领「自适应选择器」是为「每站有固定选择器」设计的，我们是 147 个站通用抓取，用不上。
  3. `scrapling install` 还要下载浏览器，正是我们卡过十几分钟的那一步。
- 验证：装 `curl_cffi` 实测（同一台机器、同一个 IP）——
  CNN 200（5.7 MB）、中新网 200，说明工具本身可用；但**路透、彭博、纽时三个全部失败，
  而且 curl 连连接都建立不起来（timeout），比 urllib 拿到的 401/403 还差**。
  真浏览器（Edge）在同一批站上同样是 401/403。三重证据指向同一结论：
  **这批站是按 IP/网络层封的，任何指纹技术都无效。**
- 影响：抓取方案维持「RSS 优先 → HTML 兜底 → 真实浏览器补漏」三层；
  剩下 22 个源要么上住宅代理（要花钱），要么放弃。`probe_url.py` 保留为诊断工具。

## 2026-10-07 加第四层：Google News RSS 兜底，不用代理

- 背景：22 个源被 IP 封，一度判断「只能上代理」，但代理要花钱，用户选了放弃。
- 选项：放弃；买代理；找第三方镜像。
- 决定：改用 `https://news.google.com/rss/search?q=site:<域名>` 取这些源的最新标题。
  境内源用 `hl=zh-CN&gl=CN`，境外源用 `hl=en-US&gl=US`。
- 原因：实测 **22/22 全部成功，每源 100 条，还带发布时间**，完全绕开原站反爬。
- 代价：链接是 `news.google.com` 的跳转链接，不是原站直链。
- 影响：覆盖面 72 → **204 / 219**。原判断「只能上代理」被推翻；
  兜底目标也从「HTML 失败的源」放宽为「库里窗口内没内容的源」。

## 2026-10-07 选稿方式要改：每源 1 条 → 按故事簇选

- 背景：`analyze_coverage.py` 把窗口内条目按标题聚类，量出「同一件事被多少家报道」。
- 数据：≥2 家的故事簇 105 个、≥3 家的 24 个；**现有 109 条选稿只覆盖 5/105、2/24**。
- 原因：`--per-source 1` 是「每个源取最新一条」，等价于随机抽样，与重要性无关。
  加条数不解决问题——每源 3 条只是把噪声放大三倍。
- 决定：选稿单位从「源」改成「故事簇」，按 `被报道家数 × 星级权重` 排序，每簇取 1–2 条代表。
- 影响：目标条数 140–180；跨语言同题需要 LLM 合并（Jaccard 只能合并同语种近似标题，
  例如「诺奖化学」英文 9 家与中文 5 家会被算成两个簇）。

## 2026-10-07 选稿改造落地：shortlist.py

- 背景：`--per-source 1` 只覆盖 8% 的重大故事簇，且加条数无效。
- 决定：加 `scripts/shortlist.py`——先聚类，再按 `家数^1.5 × 10 + 星级总和` 排序，
  每簇只占 1 个名额，按名额上限截断后交给主编判栏目。
- 修正 1：打分必须用**家数**而不是**条目数**。用条目数时，单个源把同一标题重复发很多遍
  （聚合页、栏目页）会把分数顶到第一——实测第一版第一名就是个单源导航页。
- 修正 2：`classify.py --apply-index` 回写前要先 `selected=0` 清空，
  否则上一期的选稿标记会残留（实测混进 107 条过期条目）。
- 影响：重大簇覆盖率 2/24 → **24/24（100%）**；≥2 家的簇 5/105 → **105/105**；
  一期 156 条，HTML 58 KB。

## 2026-10-08 daily-news / news-push 从全局降回项目级

- 背景：这两个 skill 是 10-07 晚装进全局 `~/.codex\skills\` 的，撞上了 `智能体配置\docs\05` 里
  「常驻白名单四个」的口径；而且它们的正文直接写死了本项目路径，本来就是只有这个项目用得上的 skill。
- 选项：留全局（每个会话都占常驻额度）；挪回项目级 `<项目>\.codex\skills\`。
- 决定：挪回项目级，全局那份移除（2026-10-08，用户批准）。
- 原因：常驻预算是稀缺资源，写死单项目路径的 skill 没有资格占；这也是 `docs\05` 划分表的原意
  （「新想法先当项目级试」）。
- 代价：只在 `D:\File\Codex\每日新闻` 目录下工作时才可见。换到别的目录喊「跑今天的新闻」，
  skill 不会出现——要么先切进本项目，要么把要做的事直接说清楚。
- 影响：`.codex\` 已加进 `.gitignore`，不会随日报推上公开仓库；这两个 skill 已纳入
  `D:\File\Codex\智能体配置\scripts\Verify-Installed.ps1` 的校验范围，
  连带查一件事：同名 skill 不许在全局和项目级各装一份。
